ER

Relational overview

All 12 tables and all 16 foreign keys, with identity fields only.

100%

Reading this diagram

  • Crow's-foot markers show cardinalities at both ends. Dashed links are non-identifying: every child table has its own surrogate primary key.
  • A user may have zero or one student profile and zero or one recruiter profile. Role exclusivity is application logic, not a database inheritance relationship.
  • The two messages-to-users links are distinct: sender_id and receiver_id.

ER

Full physical schema

Every mapped field, SQL type, key and declared nullability.

100%

Reading this diagram

  • NULL labels follow the ORM model literally. A default value does not imply NOT NULL.
  • Only recruiter_id on internships and internship_id on interviews are nullable foreign keys.
  • student_skills, applications and saved_internships have surrogate IDs but no composite pair-uniqueness constraints.
  • documents belongs to students; there is no documents-to-applications foreign key. Application resume content is stored separately in applications.resume_url.

Student, recruiter and administrator goals inside the HireHub system boundary.

100%

Reading this diagram

  • Actors remain outside the system boundary. Ellipses represent user goals; unarrowed solid lines show participation.
  • Authenticated access is a precondition for protected goals, not an include arrow to a login screen.
  • Messaging requires an existing application connection. Shared goal names appear for each participating role to keep the view readable.
  • Admin self-registration, email delivery, a calendar grid and machine-learned matching are not shown as implemented capabilities.

UML sequence

Submit an application

Internal application request, optional resume, rejection paths and both commits.

100%

Reading this diagram

  • Solid arrows are requests/calls; dashed arrows are replies. opt and alt frames show conditional behavior.
  • Authentication/token rejection and database exceptions can terminate processing; the diagram details business validation branches after successful authentication.
  • COMMIT 1 saves the application and optional document. COMMIT 2 saves alerts. These boundaries intentionally match the current code.

sequenceDiagram
    autonumber
    actor S as Student
    participant UI as React student UI
    participant API as FastAPI applications route
    participant DB as MySQL via SQLAlchemy
    S->>UI: Submit application with optional resume
    UI->>API: POST /api/applications (bearer token, multipart)
    API->>DB: Load account by token subject
    DB-->>API: Account identity
    API->>API: Check active-account flag
    API->>DB: Find student, internship, existing application
    DB-->>API: Related records and duplicate result
    alt Missing profile or internship
        API-->>UI: 404 response
    else Application already exists
        API-->>UI: 400 response
    else New application
        opt Resume supplied
            API->>API: Read resume bytes
            break Abort request if size exceeds 8 MiB
                API-->>UI: 413 response before writes
            end
            opt Non-empty file
                API->>API: Encode data URI and queue Document
            end
        end
        API->>DB: INSERT Application (+ optional Document), COMMIT 1
        DB-->>API: Application ID, refreshed record
        API->>DB: INSERT student alert (+ recruiter alert if linked), COMMIT 2
        DB-->>API: Alerts persisted
        API-->>UI: Application response with related internship
        UI-->>S: Confirmation, refresh listing/dashboard data
    end
    Note over API,DB: Application and alerts<br/>use separate commits.<br/>COMMIT 1 survives a later<br/>alert failure.<br/>Duplicate checks are not<br/>a UNIQUE constraint.
UML sequence

Schedule an interview

Recruiter scheduling with the current authorization and transaction behavior.

100%

Reading this diagram

  • Successful authentication and database writes are assumed; failures return before later steps.
  • The recruiter role dependency is implemented, but schedule_interview does not verify ownership of the submitted application. The diagram records this gap rather than inventing a check.
  • Interview persistence precedes the application status/notification commit. The meeting link is supplied data; there is no video-conferencing integration.

UML activity

Application submission activity

Guarded branches for internal/external roles and the internal API processing path.

100%

Reading this diagram

  • Filled circle: initial node. Bullseye: activity final. Rounded rectangles: actions. Diamonds: decisions. Every outgoing decision edge has a guard.
  • External applications redirect to a supplied company link; this branch does not create a local application record.
  • The internal branch assumes a valid active-account token. A rejected request ends this attempt; a user may start another attempt.
  • Application validation does not currently enforce active-post or deadline eligibility; no such checks are invented here.
